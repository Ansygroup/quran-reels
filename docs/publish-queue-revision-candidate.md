# Experimental queue revision (not integrated)

`sql/operations/candidate_publish_queue_revision.sql` is an **alternative isolated experiment** to the attempt-generation trigger. It adds a UUID revision and changes it on every insert or update, even a no-op or a client-supplied revision. A hypothetical cooperating claimant compares the read revision as well as owner, status, platform and target; a cooperating finalizer compares the new revision returned by the claim. The real `publishRow` does **not** do this and this file is not a migration. No production change is authorized by this experiment.

`tests/publish_queue_revision_candidate_pg_test.js` tests hypothetical SQL against disposable PostgreSQL: stale payload/reversal and status-ABA snapshots fail the revision predicate, concurrent claimants serialize, a previous finalizer cannot change a newer claim, an update while publishing makes the result unconfirmed, and delete/reinsert receives a different token. It also deliberately demonstrates that an old status-only finalizer can still write. Backfilling an existing `publishing` row creates a UUID but does not identify or fence its already-running legacy worker. UUID collision is extremely unlikely, not mathematically impossible.

`tests/postgrest_publish_queue_revision_candidate_test.js` uses the SQL-to-REST translator and a disposable PostgREST fixture in CI, with a separate hypothetical query, not the real publisher. It checks revision predicates and returned values, a stale claim/finalizer, and a synthetic lost claim response after commit. The loss means no worker should assume it can dispatch or safely replay; the test itself does not implement app error handling. The fixture has account-target candidate triggers and a synthetic service role, not production policies or Supabase.

**Limits and adoption risks:**

- All claim readers, claimers and finalizers must actually validate complete representations and compare the right revision. Legacy finalizers, privileged or direct writers ignoring the predicate still defeat the protection. A writer who can disable or replace the trigger can bypass it; this does not remove excessive privileges.
- Any update after claim, including a benign/no-op update, invalidates the finalizer and may turn a successful external operation into an unconfirmed result. Do not blindly retry. Nor does a revision prevent an already-sent external request, duplicate jobs, a provider response loss, or non-idempotent provider behavior.
- A volatile UUID default on an existing table may rewrite/lock it; production size, time, support for the function, privileges, concurrent trigger behavior and online migration need independent review. A synthetic backfill does not give active old workers a usable token. Rollout must drain/fence old workers, handle historical in-flight rows and mixed versions, and preserve safe rollback; adding a column alone is not a rollout plan.
- Actual app and SQL compatibility, PostgREST schema cache, RLS/ACL, client access, target/disconnect triggers, lost or malformed representations, worker time limits, and provider protocols must be tested together in an isolated environment. No provider, real authenticated user or Supabase production system was tested here.
