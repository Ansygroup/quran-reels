# Telegram publishing candidate — not enabled

This is an isolated implementation exercise, not a working integration. `lib/telegram_candidate.js` and `lib/telegram_connect_candidate.js` are not routed or called by the app; Telegram remains non-publishable in `lib/platforms.js`. No real bot, account or recipient has been contacted. Do not ask users to paste bot tokens into chat.

## Covered locally

- Bot API request/response handling, channel post permission, and conservative group video permission checks (`can_send_videos`, not merely text permission). Permission can change after inspection; an API rejection must still be handled. A private recipient must start the bot and consent; these checks do not establish consent.
- Connection handler candidate uses the authenticated owner rather than an input owner, supports Vercel's parsed body and Node streams, sends credentials only in a POST body to the app, encrypts bot credentials before storage, scopes updates by owner and destination, does not change the default or autopilot settings, and does not expose tokens. Connection persistence has only been tested with a mocked database, not actual PostgREST or production schema.
- Unknown send outcomes are reported without retry in the candidate adapter. `sql/operations/candidate_telegram_outbox.sql` proposes a separate durable one-way delivery state machine: deduplicates by user, resolved destination and video path, only claims `ready` once, and never automatically returns `sending` or `uncertain` to `ready`. Re-linking the same destination does not reset the guard. `lib/telegram_delivery_candidate.js` connects the candidate SQL contract to the sender using injected dependencies, but is not wired into the application or queue. PGlite tests exercise the integrated flow with a REST emulator and mock Telegram, including lost claim, send and finish responses; PostgreSQL 17 with two connections tests competing prepare/claim and ACLs. Neither uses PostgREST or real Telegram. The SQL is not applied to production. Duplicate protection is limited to the same owner, destination and stored path, not equivalent content uploaded under a different path.

- `lib/telegram_media_candidate.js` proposes a size-bounded streaming read from the configured Storage origin, using an owner-prefixed path and no redirects; tested only with mock streams. `lib/telegram_video_validation_candidate.js` proposes full ffprobe inspection and ffmpeg decoding of both H.264 video and AAC audio. The 1920-pixel and 300-second caps are conservative **candidate policy**, not Telegram limits; rejected files are not transcoded or trimmed. Synthetic valid, missing-audio, and truncated files were tested locally. The worker now requires a validation dependency before sending. Its end-to-end test uses real synthetic decoding but mock Storage, database and Telegram; no actual user video has been inspected. A decodable audio track does not prove it is audible or that recitation is complete or correct.
- These validator executables were temporarily installed for local testing, not added to the app or deployed. The candidate needs a supported, regularly patched FFmpeg deployment, untrusted-media process isolation and resource limits, sizing for serverless time/memory/storage, and safe cleanup after crashes. These tests do not demonstrate those operational properties.

## Required before enabling

1. User-facing connection flow, secure transport, token redaction across logs/traces/errors, rotation and revocation handling. Validate bot identity, chat membership and rights; explain that a private recipient must first initiate contact and agree to receive messages. Do not automatically enable or add a platform to an existing schedule as a side effect of connection.
2. Connect the adapter to the actual queue with a durable no-duplicate policy. Today `publishRow` accepts `failed` rows and `reclaimStalePublishing` converts old `publishing` rows to `failed`; a Telegram send that committed but lost its reply or whose worker died must never silently be retried through either the manual or cron paths. Reconciliation must identify the destination and offer an explicit user review. Design for concurrent callers, connection changes, database response loss, worker crash, and duplicate rows for the same source and target, not just a caught network error.
3. Check media integrity and actual Telegram codec/size limits before upload; a filename or MP4 header does not prove a playable video. Validate destination-specific access, storage download errors, bounded memory, and response/result ownership. Specify channel links separately from private/group messages, which may not have public links.
4. Test authenticated cross-user isolation, concurrent connection/queue operations and migrations against real PostgREST in disposable infrastructure, plus browser tests and a test-only bot after explicit authorization. Review preview/production separation before any real account is connected. The current Vercel branch preview can point at production and is not a safe test environment.
5. Stories are a separate feature. Telegram Bot API's `postStory` is for a managed business account with `can_manage_stories`; story video must satisfy Telegram's format, dimensions, duration and size rules. Do not silently trim Quran recitation to meet those limits. Channel stories require separate capability research. WhatsApp work remains deferred.

References: https://core.telegram.org/bots/api#sendvideo and https://core.telegram.org/bots/api#poststory
