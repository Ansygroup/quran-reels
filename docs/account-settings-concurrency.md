# حماية إعدادات الحساب من الحفظ المتزامن — أساس قيد الدمج

**الحالة:** الأساس مدمج، وتجربة الربط مع API والواجهة وهجرة الإجراءات موجودة على فرع العمل فقط. لم تُطبّق أي من هجرتي المراجعات على الإنتاج، ولم تُنشر تجربة الربط. الحماية الشاملة غير مكتملة؛ لا تُدمج أو تُنشر التغييرات الحالية قبل إغلاق العوائق أدناه.

## ما الذي تفعله الهجرة؟

- تضيف `settings_revision` كمعرّف عشوائي يتبدل على تغيير الحقول التي يكتبها حفظ الإعدادات أو ملكية الصف. تحديث `updated_at` وحده، المستخدم في جدولة الأتمتة، لا يغيّر المراجعة. حتى لو غيّر إعداد ثم عاد كما كان تُنتج مراجعة مختلفة.
- `save_autopilot_guarded` تحفظ إعدادات حساب وصورته الخاصة في معاملة واحدة إذا طابقت المراجعة المتوقعة. `null` تعني أن المتصفح قرأ عدم وجود صف: الإدراج المتنافس لا يطغى على إدراج سبقَه. استجابة بلا صف تعني تعارضًا، لا نجاحًا. أي خطأ في الصورة يتراجع معه تحديث الإعدادات. تغيير الخلفية إلى غير مخصصة يستخدم آلية الحذف الموجودة في قاعدة البيانات.
- صلاحية استدعاء الدالة للخادم `service_role` فقط؛ ما زال الـAPI مسؤولًا عن ربط `user_id` بالجلسة، والتحقق من كل الحقول والصورة. الدالة ليست واجهة عامة للمستخدم.
- الهجرة لا تمنع الكود القديم أو مستخدمًا له صلاحية مباشرة من تحديث صفه خارج الدالة. هذا مقصود للتوافق أثناء الانتقال، لكنه يعني أن الحماية غير شاملة بمجرد تطبيقها وحده.

## قبل التشغيل الفعلي

1. دمج الـAPI والواجهة مع الدالة: يجب استخدام مراجعة **بداية المسودة**، لا آخر قراءة خلفية؛ وإرجاع تعارض واضح مع إبقاء الصورة والحقول، وطلب مراجعة الخادم قبل الكتابة فوق إعداداته. لا تُعد المحاولة تلقائيًا. يجب التمييز بين عدم وجود صف وعدم وجود مراجعة في استجابة قديمة أو ناقصة.
2. حماية جميع طرق الكتابة ذات الصلة، بما فيها التفعيل/الإيقاف وإضافة المنصة بعد OAuth. الإيقاف الصريح يجب أن يبقى ممكنًا حتى عندما تكون المسودة قديمة، وألا يعيد تشغيل الأتمتة أو يمس باقي التخصيصات. يجب أيضًا النظر في صلاحيات الكتابة المباشرة وRLS، مع التوافق مع العملاء القدامى.
3. اختبار الاستجابات المتأخرة والمتزامنة والصورة والاسترجاع وتبديل الحساب، وعمليات الحفظ عبر PostgREST الحقيقي في بيئة اختبار معزولة. لا تكفي اختبارات PGlite أو PostgreSQL المحلية لإثبات سلوك Supabase/PostgREST الحقيقي أو إنهاء طلب متأخر بعد فقد رده.
4. خطة نشر توافقية: تطبيق الهجرة أولًا بعد مراجعة أثرها، والتحقق من صلاحيات الدالة والـtrigger وظهور المخطط لدى PostgREST؛ ثم نشر API وواجهة متوافقين. العملاء المخبأون الذين لا يرسلون المراجعة يجب أن يفشل حفظهم بأمان ويُطلب منهم تحديث الصفحة، لا أن يعودوا إلى كتابة غير محمية.
5. التأكد بعد النشر من عدم تغيير الجدول أو حالة الحسابات أو تحميل صورة أو نشر فيديو أثناء الاختبار. احتفظ بخطة تراجع لا تُزيل البيانات أو الصورة الخاصة.

## الاختبارات المنفذة

- `tests/autopilot_settings_guard_db_test.js`: PGlite محلي للتحقق من حالات التعارض والصورة والامتيازات والتراجع عن الخطأ.
- `tests/autopilot_settings_guard_pg_test.js`: PostgreSQL محلي فعلي باتصالات متزامنة، يتضمن الصلاحيات والحقول الإضافية، إضافةً إلى اختبار معالج API الحقيقي عبر محوّل محلي لاستدعاء الدوال: حفظ نُفّذ وفُقد رده، ثم محاولة قديمة وإيقاف من عميل قديم. المحوّل ليس PostgREST ولا يختبر شبكة أو JWT حقيقيين. يُضبط `PG_BIN_DIR` و`PG_LIB_DIR` لمسار نسخة PostgreSQL محلية و`NODE_PATH` لـ`pg`.

لا تستخدم هذه الاختبارات أي حسابات أو بيانات حقيقية، ولا تغيّر الإنتاج.


## تجربة الربط المحلية — عوائق تمنع النشر

- هجرة `20261114_guarded_autopilot_actions.sql` تضيف إيقافًا/تفعيلًا محروسًا وربط منصة ذريًا؛ الإيقاف يُغيّر المراجعة حتى لو كان الصف موقوفًا بالفعل، ليُبطل حفظًا متأخرًا يحمل المراجعة السابقة. إذا لم يوجد صف، ينشئ الإيقاف صفًا موقوفًا بقائمة منصات فارغة بدل السماح لحفظ أول متأخر أو ربط OAuth بإعادة التفعيل؛ اختُبر هذا السباق في PostgreSQL المحلي، وما زال يلزم فحصه على مخطط الإنتاج المعزول.
- فحص للبيانات الوصفية فقط على الإنتاج أظهر أن `authenticated` لديه حاليًا صلاحيات الجدول `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`, `MAINTAIN` بالإضافة إلى `SELECT`. لا تطبَّق RLS على `TRUNCATE`؛ وجود الصلاحية لا يثبت وجود مسار HTTP قابل للاستغلال. لم نجد منحًا منفصلة للأعمدة أو عضويات أدوار للثلاثة `anon`, `authenticated`, `service_role` وقت الفحص. لم تُغيّر أي صلاحية في الإنتاج.
- مسودة منفصلة **غير قابلة للتطبيق تلقائيًا** في `sql/operations/candidate_autopilot_client_write_revoke.sql` تزيل تلك الصلاحيات وامتيازات الأعمدة عن الأدوار العامة وتُبقي القراءة؛ تُلغي المعاملة إذا بقيت صلاحية موروثة. اختُبرت على PostgreSQL محلي، بما فيه منح أعمدة منفصلة ودور موروث، دون مس بيانات. هي تقيّد عملاء قاعدة البيانات فحسب: لا تمنع خادمًا قديمًا يعمل بـ`service_role` أو يستدعي `save_custom_reel` من تجاوز الحارس. يلزم جرد واعتماد كل مسار خدمة، وحسم إيقاف الإصدارات القديمة قبل إعلان الحماية أو تشغيل المسودة. تطبيقها قبل توافر API الجديد قد يعطل عملاء قدامى.
- فحص اتصال المنصات قبل التفعيل يتم خارج معاملة تغيير الحالة؛ قد تنفصل منصة بعد الفحص. يجب مراجعة هذا السباق وشروط الأتمتة ومسارات OAuth والجدولة القديمة قبل تقرير النشر. محليًا، اختُبر بقاء العمودين الإضافيين `daily_count` و`youtube_connection_ids` كما هما بعد الحفظ والإيقاف والربط؛ لا يظهر استخدام لهما في كود التطبيق المفحوص، لكن هذا لا يثبت غياب كتّاب خارجيين.
- اختبارات قاعدة البيانات المحلية لا تختبر Supabase. نجح اختبار PostgREST منفصل في حاويات معزولة، لكنه لا يثبت تطابق إعدادات Supabase أو كل حالات تبديل الحساب والردود المفقودة. يلزم مراجعة مخطط الإنتاج وخطة التدرّج والتراجع؛ لا تُستخدم حسابات حقيقية أو تُنشر فيديوهات للاختبار.

تحقق محلي مبدئي: `npm run pretest` نجح مع الاعتماديات المؤقتة؛ اختبارا PostgreSQL وPGlite نجحا، ومتصفح محلي بمحاكاة الشبكة اجتاز حفظًا غامضًا وتعارضًا وإيقافًا قبل المراجعة. هذه الأدلة لا تغلق العوائق أعلاه ولا تثبت الجاهزية للإنتاج.


### جرد الكتّاب في الشجرة الحالية وخطة انتقال مبدئية

- الحفظ و`set_enabled` في `api/autopilot.js` يستخدمان RPCs الجديدة محليًا؛ OAuth يستدعي `link_autopilot_platform_guarded` في `lib/autopilot.js`. كاتب الجدولة المحدد في الشجرة يحدّث `updated_at` فقط. الاختبار التاريخي `tests/e2e_rest.py` يكتب مباشرة، وليس دليلًا على عميل مستخدم أو إمكانية تشغيله بأمان على الإنتاج.
- `save_custom_reel` القديم ما زال متاحًا للخدمة، والإصدارات المنشورة أو النشطة من الـAPI قد تكتب بـ`service_role` مباشرة. حجب أدوار العميل وحده **لا يمنعها**. لا نملك جردًا يقينيًا للخدمات الخارجية أو الاستدعاءات النشطة، ولذلك الترتيب والرقابة والتراجع تحتاج اعتمادًا صريحًا قبل أي تفعيل.
- النشر المتدرج المقترح: اختبار نسخة مطابقة للمخطط في بيئة معزولة، ثم الهجرتان الإضافيتان والتحقق من schema cache، ثم نشر واجهة وخادم جديدين والتحقق من انتهاء الطلبات/الإصدارات القديمة؛ فقط بعدها يُنظر في سحب صلاحيات العميل، مع مراقبة حالات الفشل. يجب إثبات عدم وجود كتابة قديمة بـ`service_role` أو إضافة حارس قاعدة بيانات يمنعها؛ لا تعلن الحماية شاملة خلال الفجوة. التراجع إلى خادم قديم يعيد خطر الحفظ غير المحروس حتى لو بقي سحب صلاحيات العميل.
- رفضت Supabase إنشاء فرع معزول لأن الفرع يتطلب Pro أو أعلى؛ لم يُنشأ فرع ولم تتغيّر خطة الاشتراك. بدلًا من ذلك نجح اختبار PostgREST حقيقي في حاويات GitHub Actions مؤقتة، لا تتصل بـSupabase. هذا ليس اختبارًا لمزود الإنتاج ولا بديلًا عن مراجعة الفروق قبل النشر.
- اختبارات DOM إضافية `tests/account_concurrency_draft_test.js` تفحص أن تحديثًا خلفيًا لا يستبدل صورة أو اختيار كل القنوات في المسودة، وأن قراءة فاشلة أو إيقافًا جاريًا لا يجيز اعتماد مراجعة سابقة. تعتمد على `jsdom` محليًا وتستخدم شبكة محاكاة.

### تجربة حارس دور الخدمة — محلية وغير معتمدة

- أُضيفت مسودة مستقلة ثانية، `sql/operations/candidate_autopilot_service_guard.sql`، وليست هجرة تلقائية. بعد مسودة صلاحيات العميل فقط، تزيل صلاحيات كتابة `service_role` المباشرة عن صف الإعدادات والصورة، عدا تحديث `updated_at` وتحديث `enabled` المحصور بالإيقاف للصف الموجود. وتوقف تنفيذ `save_custom_reel` القديم. دوال الحفظ والتفعيل وربط OAuth الجديدة تعمل بصلاحيات مالكها؛ لا تتيح المسودة لمسودات/خوادم قديمة الحفظ أو التفعيل خارج المقارنة.
- لإبقاء إيقاف الخادم القديم ممكنًا للصف الموجود، يستخدم المقترح trigger قبل تحديث `enabled`: يسمح بالتعيين إلى `false` فقط، ويجدد المراجعة حتى لو كان الحساب موقوفًا؛ الكتابة إلى أي عمود آخر محظورة بالصلاحيات. تحديث الجدولة `updated_at` وحده لا يُبطل المسودة. الإيقاف القديم على صف غير موجود يفشل ولا ينشئ حاجزًا؛ الـAPI الجديد ينشئ صفًا موقوفًا في هذه الحالة. استدعاء دوال الخدمة نفسها يعتمد على أن مفتاح الخدمة موثوق وأن الـAPI يصادق المستخدم، ولا يحمي من مفاتيح خدمة مسرّبة أو اتصالات مالك قاعدة البيانات.
- ترفض المعاملة التطبيق إذا كانت مراجعة الصف أو ترتيب triggers غير مضمونين، أو كانت الصلاحيات موروثة، أو كان دور الخدمة مالكًا/قادرًا على تقمص مالك الدوال أو الجداول. اختُبر محليًا استخدام `service_role` بصلاحية تجاوز RLS كما في وصف دور الإنتاج، ورفض التفعيل والحفظ والصورة القديمة، مع استمرار الإيقاف القديم والحفظ والربط والصورة عبر الدوال الجديدة. اختبار باتصالين أثبت أن تركيب الحارس انتظر معاملة كتابة قديمة قائمة، وأن إيقافًا مباشرًا أبطل حفظًا لاحقًا بمراجعة قديمة. نجح اختبار PostgREST على حاويات معزولة، ولم تُختبر النسخ المنشورة أو صلاحيات Supabase الفعلية.
- قراءة بيانات وصفية للإنتاج أظهرت أن الدالتين الحاليتين اللتين يرد فيهما اسم الجدول هما تنظيف الصورة و`save_custom_reel`، ومالكهما `postgres`. هذا بحث نصي محدود وليس ضمانًا بعدم وجود وظائف ديناميكية أو كتّاب خارجيين، ولا يكفي لتبرير التطبيق. الإصدارات القديمة قد تفشل في الحفظ أو ربط OAuth بعد الحارس؛ لذلك يلزم نشر الخادم الجديد والتحقق منه أولًا وخطة للتعامل مع الإصدارات النشطة. لا تزيل الحارس أو تمنح خدمة الكتابة مجددًا ضمن تراجع صامت: التراجع إلى خادم قديم غير محروس يعيد خطر التعارض. لا تتغير بيانات أو صلاحيات الإنتاج ما لم تُعتمد الخطة وتُنفذ صراحةً.

### اختبار PostgREST عبر GitHub Actions (ناجح في بيئة معزولة)

أُعدّ `.github/workflows/postgrest-account-guard.yml` مع PostgreSQL 17 وPostgREST في حاويتين مؤقتتين، ويستخدم `tests/postgrest_fixture.sql` و`tests/postgrest_guard_http_test.js` بيانات ومفاتيح JWT اصطناعية فقط. عنوان HTTP ثابت على `127.0.0.1:3101`؛ لا تستخدم المهمة أسرار Supabase أو أي بيانات حقيقية. تُطبَّق ملفات SQL المقترحة داخل حاوية الاختبار فقط، وتُختبر استجابة RPC الفعلية وRLS والحجب والإيقاف والحفظ المتزامن. تحميل SQL في PostgreSQL محلي نجح. تشغيل GitHub Actions رقم 43416977566 نجح على commit 9a010cc2، بما في ذلك مرحلتا HTTP foundation وguarded وتطبيق المسودات في الحاوية فقط؛ بيانات الخطوات تؤكد النجاح، لكن تنزيل السجل التفصيلي غير متاح من بيئة العمل. هذا لا يُثبت تطابق إعدادات Supabase الإنتاجية أو يجيز النشر دون مراجعة التدرّج.

### تكامل API مع PostgREST المعزول (ناجح باعتماد هوية محاكاة)

أُضيف `tests/postgrest_account_api_integration_test.js` لاستخدام معالج الحساب و`lib/db.js` الفعليين مع PostgREST محلي. يقيّد وسيط الاختبار نفسه بمسارات إعدادات محددة و`127.0.0.1` فقط، ويستخدم هوية ومفاتيح وهمية؛ المصادقة محاكاة وليست اختبارًا لـSupabase Auth. يتضمن حفظين متنافسين، ومعرّف مستخدم مزورًا في جسم الطلب، وردًا مفقودًا بعد تأكيد قاعدة البيانات، والإيقاف من عميل قديم. نجح تشغيل GitHub Actions رقم 43418021104 على commit 82cda46f بعد أن عُدّل اختبار التزامن ليجعل كلا الحفظين يغيّر الإعدادات فعلًا. فشل التشغيل السابق ولا يُعد دليل نجاح؛ حالة خطوات التشغيل الجديد ناجحة، ولم يتوفر تنزيل السجل التفصيلي في بيئة العمل. لا يختبر ذلك المصادقة الحقيقية أو PostgREST في Supabase.


### تنبيه المعاينة الحالية

Vercel ينشئ معاينة لفرع العمل تلقائيًا، وهي تستخدم عنوان قاعدة بيانات الإنتاج وفق إعدادات المشروع، بينما هجرة المراجعات لم تطبّق على تلك القاعدة. **لا تستخدم المعاينة الحالية لتسجيل الدخول أو ربط قنوات أو حفظ الإعدادات أو التشغيل.** اختبارات GitHub المذكورة أعلاه تعمل فقط على حاويات وهمية منفصلة؛ لم نختبر أو نغيّر أي حساب في المعاينة.
