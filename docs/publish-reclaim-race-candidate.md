# Publish reclaim race: local evidence and candidate only

The current publisher claims a row by status and target and finalizes using `id`, `user_id` and `status='publishing'`; reclaim marks old publishing rows failed after 20 minutes. Reclaim is not cancellation: a worker or provider request can continue after the row has been marked failed. Under the current failed-row guard, a normal attempt to publish that failed row stops for review. If nobody reactivates it, the old finalization returns `result-unconfirmed`; the external operation might nevertheless have succeeded.

`tests/publish_reclaim_race_test.js` exercises the actual publisher, REST translation and reclaim function with synthetic in-memory responses. It also demonstrates an ABA limitation by deliberately simulating an **independent uncoordinated writer** that changes the failed row back to scheduled while the first provider request remains in flight. A second worker then claims it; the old worker can finalize against the new `publishing` state, and the newer worker's result is unconfirmed. The test does not establish that this transition is reachable through the current failed-row retry path, or that it occurred in production. It does not send real requests.

A separate stale scheduled snapshot can also be claimed after independent reactivation, so the candidate generation alone cannot fence the initial claim; see `docs/publish-queue-writer-audit.md` for the local writer inventory and fixture permission test.

`sql/operations/candidate_publish_attempt_generation.sql` and `tests/publish_attempt_generation_candidate_pg_test.js` are an **unwired candidate**, exercised only against disposable PostgreSQL. The trigger assigns a new generation whenever a row enters `publishing`, preserves it while that claim stays active, and clears it on exit. The test uses hypothetical cooperating claim/finalize SQL: a stale generation cannot finalize a newer claim; an old finalizer without the generation predicate still can. Pre-existing publishing rows have no generation and require review, not a guessed token. The candidate must not be applied to production as a migration.

Even a fully coordinated database generation would only fence database finalization; it cannot cancel or deduplicate external requests, guarantee no duplicate posts, prove a provider result, or stop a legacy writer bypassing the predicate. An ambiguous claim or result response still requires review rather than retry. Before considering implementation or rollout, audit **all** queue writers, direct table grants and RLS, legacy application instances, disconnect and retry workflows, trigger interactions, reclaim/claim serialization, UUID support, RPC/REST representation and deployment compatibility. Plan for in-flight and legacy NULL claims; the local test covers both reclaim-first and finalization-first row-lock ordering, but production and PostgREST behavior still need verification. Any adoption needs schema and application changes coordinated across every writer, isolated PostgREST and provider-specific tests, a safe deployment and rollback plan, and explicit approval; none is done here.
