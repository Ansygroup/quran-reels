# Per-batch publish concurrency candidate (not wired)

Current `publishTargets` launches the entire confirmed draft batch at once using `Promise.allSettled`. `lib/publish_batch_limit_candidate.js` is an **unconnected local experiment**, not a replacement in the app: it accepts a caller-supplied concurrency limit, a confirmed draft batch and an injected publisher. It validates all entries before invoking any publisher, checks owner/target consistency and duplicate row IDs/target pairs, makes shallow snapshots, and processes at most that many targets at once in this invocation. A failed or thrown result does not automatically retry or cancel other targets; results remain in input order. It conservatively treats a non-boolean success or missing URL as unconfirmed. An explicit success plus URL still does not prove a provider has published a video.

`tests/publish_batch_limit_candidate_test.js` exercises concurrency 1 and 2, shuffled completion, a simulated lost response, partial failures, invalid/mixed/duplicate batches and no-retry behavior using synthetic promises. `tests/publish_batch_limit_publisher_candidate_test.js` connects the experimental orchestration to the **actual `publishRow` only inside the test**, using a mocked database, synthetic storage bytes and fake YouTube responses. One fake provider response is lost, another final update commits but its response is lost, and a third succeeds; each claim, upload and final update is attempted once. No real requests or videos are involved. The candidate is not imported by `lib/autopilot.js` and the separate bounded reader is not integrated.

**Important limits:**

- This limits only publisher calls in one invocation; multiple workers, users or cron instances can exceed it. It does not bound aggregate memory or govern independently running jobs.
- Waiting targets remain drafts and may never start if the worker crashes or its execution budget expires. Existing workers may already be sending; a crash cannot cancel provider operations. Recovery requires durable per-target evidence and human review for ambiguous operations, not automatic retry. There is no durable scheduler, lease or fencing in this candidate.
- A slot is occupied for the entire publisher call; an operation that never resolves blocks the batch. No task timeout or cancellation is introduced. Provider requests may continue after any future abort, so a timeout cannot establish non-publication.
- Limits affect completion latency and platform rate behavior. A per-read cap, per-batch limit and actual runtime memory are separate concerns. The proper number depends on deployment, independent processes, provider contracts and video sizes; no production limit is chosen.
- Before integration, review how partial results, waiting drafts, lost claim/finalization responses and invocation termination reach `autopilot_runs`; test multi-process contention, recovery, permissions, deployment compatibility and rollback in an isolated environment. Do not infer exactly-once publication from this experiment.
