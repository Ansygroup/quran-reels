# Account disconnect and queue target — candidate design, not deployed

## Problem and current behavior

The production foreign key observed on `publish_queue.connection_id` is `ON DELETE SET NULL`. A subsequent publisher can choose the current default or the most recently updated connection for a NULL target. A channel deletion therefore risks redirecting an existing job. NULL also appears in old failed/published rows and does not reveal the original channel. A user-facing warning and checking for rows before a separate delete do not make the operation atomic. The live disconnect implementation has a pre-parsed-body problem and does not verify that a row was deleted. The owner chose to retain the disconnect option with a warning rather than temporarily disable it. The proposed branch handler now accepts pre-parsed or streamed bounded JSON and confirms one owner-scoped deletion through a minimal returned representation; the UI requires that evidence and treats lost responses and old-server success replies as uncertain. This makes the current button capable of deleting on platforms where its body was previously mishandled. It does not resolve any queue race, stop a worker already holding credentials, prove provider revocation or prevent direct/old-client writes. Stopping automation does not cancel existing queue entries or an upload already in progress.

## Disposable prototype

`sql/operations/candidate_account_disconnect.sql` is **not a migration** and is not connected to the app. Alongside the separate experimental queue trigger, it serializes cooperative default/insert/disconnect operations with the same user/platform advisory lock. It rechecks ownership after locking, returns `not_found` for a different owner's channel, and refuses to delete if any queue row explicitly references the channel or any same-user/platform row has an unknown NULL target. A repeat after deletion returns `not_found`, not proof of whether a prior request succeeded. Only the service role can call it in the fixture; the real HTTP handler must authenticate and derive the user ID itself, never trust a caller-supplied user ID.

This deliberately strict policy blocks deletion even for published or cancelled history, and unknown historical rows can block all connections for that platform. It is useful for demonstrating the database safety constraint, **not acceptable as a finished disconnect feature**. Do not erase queue evidence to make it pass. In particular, a prior read-only production snapshot contained 18 failed and 7 published YouTube rows with NULL connection IDs; the snapshot may have changed and cannot identify their owners or historical destinations.

`tests/account_disconnect_candidate_pg_test.js` runs only against disposable local PostgreSQL. It exercises wrong-owner/role rejection, legacy NULL and referenced statuses, rollback, insert-first and disconnect-first races. It also demonstrates that the RPC **alone** loses a race against an unguarded NULL insert. `tests/account_channel_fixture_pg_test.js` additionally loads the exact HTTP job's fixture and candidate SQL into a disposable Unix-socket-only PostgreSQL 17 cluster, tests role/claim isolation, table/column denial, service RPC and both guarded insert/disconnect orderings using direct SQL. `tests/postgrest_channel_candidate_http_test.js` passed against disposable PostgREST in GitHub Actions; none of those tests exercise production Supabase Auth or provider revocation. `tests/account_disconnect_api_test.js` tests the new routed handler and REST requests with a synthetic database, including an already-committed deletion with a lost response. A separate fixture test (`tests/postgrest_disconnect_api_integration_test.js`) is prepared to exercise that handler against disposable PostgREST with mock auth; check CI for its actual result.

## Requirements for a usable production design

1. **Explicit destination and server-owned evidence.** New jobs must persist a validated owner/platform/channel identity, with default resolution ordered against all changes to that default. Reject new missing or ambiguous defaults instead of falling back to the latest channel. Preserve already existing unknown-target rows for review; never assign their target from today's default. Account for all API, OAuth, cron, manual, legacy/direct PostgREST and service-role writers before rollout. A lock is only effective when all relevant paths or database guards participate.
2. **Disconnected state without destroying history.** Design a tombstone/lifecycle that can retain the minimum information necessary to identify historical targets and audit unknown outcomes without retaining unnecessary credentials. Define access, retention and deletion policy explicitly. The prototype does not implement this schema and deletion cannot simply be turned on for referenced rows.
3. **Jobs and workers.** Show affected jobs and obtain explicit user intent for any cancellations, using conditional, atomic state changes. Queued jobs, already-claimed jobs, completed jobs and unknown provider outcomes need distinct handling. A worker may already hold a token or have delivered data to a provider; a DB lock or deletion alone cannot recall it. Coordinate worker claims, account state, provider-side reconciliation and any in-flight drain; treat a lost response as unknown, not definitely unsent. Do not promise that a disconnect cancels an upload already sent.
4. **Credentials and provider consent.** Separately define local credential deletion and provider-side revocation, including failure/timeout and already-issued token behavior per provider. Do not say a provider grant was revoked just because local state changed. Re-link must not resurrect stale work or silently alter a paused automation; decide and explain whether linking may create or extend automation.
5. **Privileges and compatibility.** Review owner RLS, table and column grants, role inheritance, `service_role`, old cached clients and third-party integrations. The separate candidate ACL revokes direct access and can break integrations. Rehearse mixed-version behavior and prevent bypass before relying on a trigger or endpoint. A privileged or legacy writer can otherwise invalidate the model.
6. **Operational rollout and recovery.** Inventory statuses and NULLs without exporting secrets; agree an explicit legacy and retention policy. Rehearse migrations, role grants, rollout order, monitoring, idempotency/uncertain responses, and rollback using disposable PostgreSQL/PostgREST and real staging providers. A rollback must not unpin or redirect jobs created under the new model. Production migration, permission revocation, live disconnect and provider tests all require an approved plan.

Until those conditions are met, this repository's local UI warnings and candidate SQL should not be described as a guarantee of safe disconnect or as complete Telegram/WhatsApp integration.
