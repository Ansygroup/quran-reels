# Account page review — work in progress, not deployed

Scope: account dashboard UI and its account API, connection controls, manual scheduling link, OAuth start, run history and status. This is a code and mocked-interaction review; it is **not** a complete production audit or a real user/provider test. The branch preview can use production Supabase and must not be used for destructive tests.

## Changes in this review

- Show queued runs as pending instead of failed; show multiple destination URLs separately, safely; clarify that an upload accepted by a platform does not prove processing or playback.
- Distinguish an unavailable run history or stats query from a truly empty history or zero counts. Missing platform capability data fails closed rather than enabling every platform in the UI.
- Indicate unknown channel status on failed reads; prevent an older channel-list response from replacing a newer one; warn when enabled settings lack selected channel connections or usable refresh credentials. Failed account refreshes now warn that visible status, history and jobs may be stale, while preserving the unsaved draft. On an observed auth identity change, including a `storage` event, old account data, notice and review text are cleared synchronously and pending reads are invalidated; the same-user token refresh does not reload. Connection list, OAuth start and disconnect UI recheck the active account around asynchronous work; a late result cannot intentionally render, toast or redirect into a newly detected session. A request already sent may still complete on the server, and an OAuth-start response can already have set its state cookie; this is not a transactional or cross-tab guarantee. The connection card also warns that linking can create an enabled automation or add a platform to existing settings; it does not prevent already-enabled jobs from running.
- The new OAuth start uses an authenticated same-origin POST and an HttpOnly signed state cookie; the session token is not in the new client's URL. The client now bounds token lookup, identity checks, response and parsing to 20 seconds; late responses cannot initiate navigation, and only one start per tab is allowed while an attempt is pending, even across rerenders and Meta's shared provider. An identity change invalidates the pending result. These are browser safeguards, not transactional cancellation: an already sent request may still set a state cookie after timeout or interfere with a later attempt, particularly across tabs. The old GET URL remains for compatibility with cached clients and still carries a token; retire it only after a compatible rollout and cache transition. Actual provider redirect/callback remains untested here.
- OAuth return flags are untrusted URL text, not evidence that a channel is linked to the active account. The local UI now describes them as indications and asks the user to review the current account's channel list and automation; it also warns that a Meta store failure can follow partial changes. Old success/failure links, duplicated flags and unrelated query parameters are covered by DOM and Chromium tests. The UI does not verify the original OAuth user or guarantee a fresh list.
- Locally, `stCookieValid` now enforces the signed issuance timestamp with a 15-minute maximum age, matching the cookie's Max-Age, and allows up to 60 seconds of future clock skew. A timestamp at or beyond the age limit, missing/non-integer/invalid times and malformed percent-encoded cookies fail closed before token exchange. Clock differences can still make a valid browser attempt expire earlier or reject an attempt more than 60 seconds in the future; server time must be synchronized. `tests/oauth_state_deadline_test.js` tests start and routed callback for all four providers with a fake clock, auth, provider and database. This is not one-time consumption: two callbacks inside the window can both reach the provider, as the test deliberately shows. The callback uses the original cookie user and does not verify the active app session at return, so signing out or switching accounts does not cancel an already started flow. Provider authorization-code handling, concurrency, logout invalidation, and real-provider behavior need a separate design and tests; no production change was made.
- Locally, X and TikTok callbacks require a successful token response and a successful account-profile response containing a nonempty provider ID before writing a connection, choosing a default or enabling automation. TikTok also rejects conflicting token/profile IDs; if the token omits its ID, a valid profile ID is used. The old `me` placeholder is rejected, and an identity failure is reported as uncertain rather than a successful link. `tests/oauth_identity_guard_test.js` covers malformed/error/missing identities, conflicting IDs, provider failures, multiple IDs, store failures and no automation side effects with mocked providers and database. These checks may refuse a link when profile access is unavailable or permissions are insufficient; they do not verify capabilities or repair old placeholder records. They have not been tested with real providers. No existing records were modified.
- X and TikTok callback upserts now locally omit `refresh_token` from the conflict update when the provider omits it; a newly inserted row still contains an encrypted empty value, while a supplied nonempty refresh token is encrypted and stored. Malformed refresh-token values fail before writing. This does not rely on reading an old token and preserves whichever value is present at PATCH time. `tests/oauth_refresh_preservation_test.js` exercises the actual `lib/db.js` REST translator with mocked provider/PostgREST traffic, including controlled competing callbacks, read failure and a unique-insert collision; `tests/oauth_refresh_sql_test.js` executes the generated SQL in disposable PGlite. Neither test exercises real PostgREST, PostgreSQL wire access or providers. **Not an atomic OAuth/relink solution:** the translator performs a read followed by PATCH or INSERT; a concurrent older callback can still overwrite the access token after a newer callback, as the test explicitly demonstrates. A refresh token retained from an earlier grant may already be revoked or incompatible with the new grant. `refreshIfNeeded` can also write a stale captured refresh token after a concurrent relink or refresh. No server-owned per-connection concurrency guard or provider-level rotation protocol exists; a missing-row PATCH may also affect zero rows without the callback checking the count. Review the entire callback/refresh/disconnect/publisher lifecycle and rollout before claiming safety; no production changes were made.
- Locally, Meta callback now requires successful initial and extended token exchanges and exactly one returned, unpaginated Facebook page with a valid ID and page token. It rejects malformed Instagram IDs before writing, instead of creating a `me` placeholder or silently choosing the first of multiple/incompletely fetched pages. Until a page selector is designed, users with multiple accessible pages cannot use this new local path; the UI explains this. If the extended token response omits a valid expiry, the stored expiry is unknown rather than an assumed 60 days. Failures to enable Instagram automation now contribute to `auto_error`. `tests/oauth_meta_identity_test.js` uses mocked providers and DB, checking invalid/multiple/paginated pages, token and read failures, actual chosen IDs, automation reporting and an Instagram-store failure. This is not a transactional fix: Facebook may already be stored and automation enabled when Instagram storage fails; the callback still does not distinguish whether the user initiated Facebook or Instagram, and can complete with no Instagram account. Successful page lookup does not prove posting permissions or that the user intended the page. The existing publishing, default selection, OAuth state/relink races and legacy records need coordinated review. No real Meta API or production data was used.
- `sql/operations/candidate_connection_refresh_commit.sql` is an unwired, non-migration CAS prototype to reject refresh writes after a credential snapshot changes. `tests/connection_refresh_candidate_pg_test.js` exercises it against disposable PostgreSQL, including real competing transactions and intentionally demonstrates unguarded later writes and identical-row ABA. It is not a fix for concurrent provider refresh or legacy writers. See `docs/connection-refresh-design.md` for timestamp precision, stale reauth errors, provider-side rotation, ACL and rollout blockers. Do not apply to production.
- The local account UI now describes `reauth` as a prior platform-level refresh failure, not proof the current connection expired; it no longer labels every individual channel on that platform as expired. An unreadable/absent saved refresh credential gets a separate per-channel warning and is not proof of the provider's present state. Unknown legacy errors no longer default to YouTube. `tests/reauth_stale_failure_test.js` deliberately reproduces both a late old-credential `invalid_grant` marker and a late queue error being attributed to the platform after relinking; `tests/reauth_warning_browser_test.js` covers the wording with two synthetic channels. These UI changes do not fix the server race or prove any current credential is valid; an actual failure still warrants reviewing the provider account and configuration.
- Existing-channel connect controls now say “attempt to relink” and explain that provider selection, not the clicked channel, determines which account is returned: relinking may add/update a different channel, and adding may update an existing one. A confirmation before relink/add warns of that and of possible automation changes, including Meta's shared flow. Cancellation, a failed dialog, a detached button or an observed account/generation change sends no request. `tests/account_reconnect_intent_test.js` covers these paths and delayed identity changes with mocks; `tests/reauth_warning_browser_test.js` exercises native cancel/accept dialogs in Chromium against fake network. The deadline starts after confirmation. This is informed consent only: no channel ID is passed or verified in the callback, no exact account is enforced, and the backend's existing automation, concurrency and provider-side risks remain. First-time connect retains its existing start path.
- Remove the circular manual-scheduling instruction: that button now says manual scheduling is unavailable. A downloaded video can still be posted manually; no new scheduling feature was built.
- The default-channel button is visibly disabled: `api/gw.js` does not route `default`, and the existing handler uses separate clear/set writes. Simply exposing it could temporarily leave no default or misdirect a concurrent publish. Existing publisher falls back to the latest channel when none is default. Do not expose the handler until there is an atomic operation, a safe publisher fallback policy, and concurrent and real PostgREST tests.
- `publishRow` now rejects every failed row before claiming or uploading, including calls carrying an expected connection. The legacy `ensureQueueRow` helper (currently only used by tests) also refuses to reschedule a failed row. The YouTube callback no longer retries old jobs when relinking, and the old relink entry point returns `review_required` without network or database access. The UI says to review failed attempts; its check button looks only at today's failed automation rows, and can mark stale `publishing` rows as failed before checking, but currently does not retry them. A separate read-only owner-scoped list displays the latest 20 failed queue entries and the current name for a recorded channel when it can be resolved, clearly marking missing targets and unavailable/truncated results; a current association does not establish the historical destination. The list has no resend button. This deliberately sacrifices automatic recovery of definite failures until durable server-owned evidence and a safe user review flow exist. It does not prevent direct database mutations, a scheduled row being maliciously changed, or duplicate rows/new runs; those remain rollout blockers. Linking can still enable default automation and thus cause new scheduled publishing, independently of these failed-row guards.

- The account API and dashboard show owner-scoped, read-only snapshots of up to 20 pending queue entries (scheduled, publishing and draft) and 20 failures. Missing targets warn that current publishing may select another channel; a worker already in flight may already have chosen one. The display is not a cancellation, a live guarantee or a safeguard against races. Malformed queue records missing a target field, ID or platform now make the snapshot unavailable instead of treating an omitted target as SQL NULL; the browser also rejects malformed or contradictory review entries. A recorded ID with no resolvable name is not presented as proof the channel was deleted. A timeout or inaccessible read is not treated as an empty list. Both snapshot headings warn that lists may be incomplete, including when a server row cap hides the 21st row used for truncation detection; an empty result is not proof of an empty queue or history. Snapshots are separate reads, not a transaction or a full history. Review timestamps without an explicit date and zone are reported unavailable rather than mislabeled as Cairo. Disconnect confirmation warns of retargeting and already-running uploads. Elsewhere, a time without a date is shown in UTC rather than converting against an arbitrary January date; dated timestamps use the Cairo timezone rules available in the browser.
- The local channel dashboard now distinguishes the server-reported automation mode from an unsaved editor draft and describes delayed selection: new single-channel automation tasks have no pinned connection, so the publishing worker chooses a default at execution or falls back to the most recently updated connection. Equal or invalid timestamps and multiple defaults make the exact choice uncertain. Each channel group describes only the loaded snapshot, not the destination of existing jobs; the list can be stale or incomplete. With all-channels enabled, planning uses specific connection IDs and refuses incomplete channel data, but this is not proof of delivery. The single-mode status warns when the loaded defaults are absent, multiple or unknown; other warnings can take precedence. The list API no longer converts missing/unrecognized default values to false. The account API itself normalizes an existing row's `all_channels` to a boolean and omits it from its no-row defaults, so the interface cannot distinguish malformed persisted values that the API has already normalized; an omitted mode is shown as unknown. Neither the worker's selection nor the disabled default-change control was changed.

## Read-only production inspection (point-in-time)

- The current `publish_queue` snapshot contains 1 YouTube draft and 18 failed rows with NULL connection IDs, plus 7 published rows with NULL IDs and 12 published rows with IDs. NULL cannot establish which channel originally received an upload. Do not bulk-assign targets or retry based on current defaults.
- The actual `publish_queue_connection_id_fkey` is `ON DELETE SET NULL`. The authenticated role has table privileges including SELECT and writes on both `social_connections` and `publish_queue`, with owner-scoped ALL RLS policies. The social-connection SELECT grant includes token columns: API response sanitization alone does not prevent authenticated direct selection of the owner's stored values, whether those values are encrypted or not. PostgreSQL TRUNCATE does not honor RLS; the observed privilege is not proof of a usable PostgREST TRUNCATE endpoint or direct SQL access.
- `sql/operations/candidate_account_table_acl.sql` is a **non-applied** proposal to revoke all direct anon/authenticated access to those tables, leaving the service role unchanged. It checks table and separate column privileges, and aborts if role inheritance still grants access. This can break existing clients/integrations; inventory and owner-approved rollout/rollback are required. Isolated PostgreSQL tests cover RLS, inherited grants, TRUNCATE behavior with direct SQL, revocation, service access, and the exact channel HTTP fixture through direct SQL including guarded disconnect races. A separate GitHub Actions job exercises the fixture through isolated PostgREST; its channel HTTP cases passed in runs `43544619129` and `43544842217`, but are not proof of production compatibility.

## Important remaining risks and gaps

1. **Account settings:** the two additive revision and action migrations were applied to production with user approval, but the guarded API/UI in this branch is not deployed. The new SQL objects and function grants were verified through read-only database metadata, not production PostgREST calls. Old writers, direct permissions, rollback and disconnect interactions remain risks; the new functions alone do not enforce all writers. Do not use the production-backed preview for account testing.
2. **Disconnect:** the previously deployed `soc_disconnect` reads only the request stream and does not confirm a deleted row. The proposed branch handler accepts pre-parsed or streamed bounded bodies and only reports success after one owner-scoped deletion is returned; a missing or lost representation is uncertain. This can make the button actually delete a channel on hosts that pre-parse the body. The owner chose to retain the option with a warning, not an atomic queue guarantee. The browser timeout covers token and identity lookups, network response and body parsing; a delayed continuation cannot send a request after the deadline, and the same channel cannot be submitted again while its attempt is pending even if the list rerenders. Before sending it reports no request was sent; after sending it reports an uncertain outcome and asks for review. If the identity lookup itself cannot complete, the UI avoids showing an old account's message to a potentially different account. After timeout the button becomes available again; a request already sent might still complete, so a retry or a later list read is not proof of safety. These are per-tab UI mitigations only; aborting does not prove the server did not complete the request. The queue foreign key can set `connection_id` to null on deletion, while publishing can fall back to a different channel. Fix needs a coordinated, atomic policy for queued/in-flight jobs and explicit user messaging, not just making the body parser work. `sql/operations/candidate_account_disconnect.sql` is an isolated, unwired prototype paired with the candidate target guard; its very conservative policy blocks deletion for all referenced history and legacy NULL rows, so it is not a finished disconnect solution. Disposable PostgreSQL tests cover insert/delete ordering and deliberately demonstrate the unguarded legacy insert race; candidate PostgREST HTTP cases passed in isolated GitHub Actions, not against production. See `docs/account-disconnect-design.md` for requirements and tradeoffs. No production schema changes were made here. Revoking provider access is a separate action from deleting the stored token.
3. **Default channel:** no routed, atomic implementation currently; the disabled control is a stopgap. `sql/operations/candidate_account_default.sql` is an isolated CAS/locking prototype, and `candidate_account_queue_target.sql` proposes pinning inserted jobs to an owned default and rejecting silent target changes. A disposable PostgreSQL concurrency test demonstrates both that the default RPC alone has a legacy-insert race and that the candidate trigger pins new targets when insert and default change compete. **Neither is a migration or wired in.** Existing NULL jobs cannot safely be inferred, deletion of referenced channels is blocked even for historical rows, and an upload already handed to a worker may continue. The `ensureQueueRow` helper searches for NULL when using a default target; it currently appears to be used only by tests, but would be unsafe if reused with this trigger. Actual queue/retry deduplication paths must also be reviewed before installation. Legacy direct default changes, reconnect/ensureDefault, disconnect, queue writers, deduplication, RLS/service privileges and actual PostgREST need a coordinated design and rollout; test triggers cannot solve those by themselves.
4. **Queue claim and unknown upload outcomes:** the proposed branch claims a scheduled/draft row only if its owner, status, platform and explicit connection (including NULL) still match the caller's snapshot; missing target information or an inconsistent returned row stops dispatch. This rejects target changes observed before that claim, but does not lock the channel or default afterwards. A later worker reading a NULL target can still choose a default/latest connection, and a disconnect or uncoordinated writer can race with an already claimed job. An unconfirmed claim can leave a row publishing until recovery; review it rather than assuming nothing happened. Final success/failure updates are now owner- and `publishing`-scoped and their returned row is checked. A missing or lost update response is uncertain, with no second write to `failed` after a potentially committed success; provider failure still doesn't prove that no video arrived. These checks are not per-attempt fencing: an old worker could still affect a later attempt if an uncoordinated writer changes the row back to `publishing`. Provider completion and external side effects are not verified by database status. For the automation run ledger, the branch also requires an owner-scoped `rendering` → `queued` marker including the video path before inserting queue targets, and confirms `queued` → final state. A lost, missing or inconsistent run-transition reply stops the current publish attempt and is not followed by a blind failed-state overwrite; an already committed transition may leave a run queued or final and requires review. A direct SQL metadata read found the required run columns in production, not PostgREST cache or runtime behavior. These state checks have no per-attempt fencing and do not coordinate old writers. The real queue's recovery and retry policies need review across platforms; the separate Telegram candidate does not guard the actual queue. Avoid automatic retry when a provider may have accepted the upload without responding.
5. **Authentication and OAuth:** compatibility GET still accepts the session in a URL; other clients and cached service workers must migrate before retiring it. The local account UI now offers confirmed sign-out: it clears the current in-memory session immediately and attempts to remove localStorage, reports storage failure, and sends the captured access token to Supabase logout with `scope=local` and a 12-second deadline. Network failure, a rejected or expired access token and timeout are uncertain, not proof of remote revocation. A successful response does not immediately invalidate already issued access JWTs; other services may accept them until expiry. Logout does not stop automation or queued jobs. Session revisions reject late refresh/user lookup responses and concurrent refreshes in one tab share a request. Before using a token, acting on logout, or committing a refresh or hydration response, the client also checks the current stored value when readable, rather than relying only on delivery of a storage event. If a changed session is detected at logout, the newer session is retained and the user is prompted to review it. A real Chromium two-tab test holds storage events deliberately and checks that an already-observed logout is not overwritten by a mocked delayed refresh. **This is best-effort, not cross-tab synchronization:** localStorage read and write are not atomic, storage may be inaccessible, another tab can write after the check, and concurrent refresh requests in different tabs are not single-flight. An already sent logout can revoke a newly restored copy of the same server session; an expired token or in-flight refresh may make remote logout uncertain. Do not claim all devices, tabs, refresh tokens or JWTs are immediately invalidated. The tests use mock auth responses, not real Supabase. Verify start/callback cookies, state, session and redirects against each real provider in an isolated environment. Avoid leaking URLs/tokens via logs.
6. **Status accuracy and TikTok:** YouTube processing, availability and playback are not confirmed by a returned video ID. Check YouTube Studio for the reported playback issue; other providers may also process asynchronously. Previously a TikTok initialization reply without an upload URL caused an unconditional second initialization with `PUBLICLY_VISIBLE`, even if the first reply did not establish a privacy rejection. The owner chose to remove that fallback; this branch sends at most one initialization request, and a failed, malformed, incomplete or lost initialization reply is reported as uncertain without uploading. The first request's existing `SELF_ONLY_DISABLE` value is not among the documented [Direct Post privacy values](https://developers.tiktok.com/doc/content-posting-api-reference-direct-post?enter_method=left_navigation), and the existing `source_info` lacks the documented required `source` field. TikTok's [sharing guidelines](https://developers.tiktok.com/doc/content-sharing-guidelines?enter_method=left_navigation) require creator-info-based privacy options, a manual privacy selection with no default and express consent before sending materials. The current automatic workflow does not establish these steps. Do not fix this by silently hardcoding another privacy value: that could change visibility or start actual posting without the required choice. A production read-only aggregate at one point in time returned zero TikTok connections, enabled autopilots including TikTok, open queue rows and failed queue rows; that is not a guarantee about later activity or external systems. A successful upload PUT is still not proof of final publication. The implementation needs a product/rollout decision, compliant consent and privacy handling, provider-specific status and URL handling, then isolated tests and separately authorized real-provider validation before asserting support.
7. **Completeness:** manual video scheduling, Telegram/WhatsApp delivery, and Telegram stories remain unavailable. Verify accessibility, keyboard/RTL behavior, mobile and desktop in real browsers, real authenticated cross-user isolation, failure/recovery paths and all provider capabilities before calling the page complete. The homepage and static FAQ, the scheduling article and selected blog passages now qualify account/connection claims and correct automatic scheduling and direct Telegram/WhatsApp availability; their generators were updated too. `tests/static_account_copy_test.js` regenerates selected pages in an isolated temporary directory and compares their visible content, metadata and FAQ schema; this wording change does not fix the underlying risks. Other site content still contains overconfident or outdated statements and needs a separate audit.
8. **Offline navigation:** the previous service worker wrote every same-origin navigation response into the `/` cache key, so articles and error pages could replace the app shell. Locally, `qr-v70` caches the shell only from a successful, non-redirected HTML response for the query-free root; install applies the same validation and does not let failed assets block activation. Root SPA navigation can use that shell offline, but static pages intentionally return a network error when offline instead of masquerading as the homepage. Query-bearing responses are not stored as the shared shell. If shell installation fails and a valid root has not subsequently been fetched, offline root navigation also fails; this is not a guarantee that audio, account actions or all site content work offline. `tests/sw_navigation_browser_test.js` exercises install, failed assets, errors, redirects, query strings, updates and offline navigation with a real Chromium service worker against a synthetic local server. No production service worker has been updated.

- Before dispatch, the publisher now checks every returned connection has a unique ID and the expected owner and platform; malformed, duplicate, foreign-owner or wrong-platform responses fail the claimed job rather than selecting a different connection or contacting a provider. `tests/publish_connection_scope_test.js` reproduces these responses with fake credentials and proves no provider request is sent; ordinary valid responses are covered separately by mocked publish tests. This is defense in depth, not proof that production returned incorrect rows, and does not lock connections or prevent changes after the read. A rejected job is marked failed and requires review rather than automatic retry.
- YouTube, Facebook, Instagram and X responses must now include a nonempty string identifier containing only ASCII letters, digits, underscore or hyphen (up to 256 characters) before the corresponding stage is accepted. An invalid Instagram container or X media ID also blocks the follow-on publish call. `tests/publish_provider_response_test.js` covers malformed and valid synthetic responses; it does not test real providers. A rejected response may still follow a provider-side success and is marked failed for manual review, not automatic retry. This conservative character rule could reject an unexpected legitimate provider format; verify against real provider responses before rollout. A valid ID is not proof of completion or playback. TikTok handling and its unresolved privacy/status requirements are unchanged.
- TikTok initialisation now requires an explicit `error.code` of `ok`, an object containing a nonempty `publish_id`, a valid upload URL, and no contradictory extra errors; otherwise the job fails for review without sending video bytes or retrying with public privacy. `tests/tiktok_init_guard_test.js` exercises malformed, missing and contradictory replies using fixtures. The documented successful response includes `error.code: ok` and a publish ID ([TikTok Direct Post example](https://developers.tiktok.com/doc/content-posting-api-reference-direct-post)); compatibility with actual provider responses remains untested. This guard **does not resolve completion tracking**: after an accepted PUT the current code marks the queue row `published` without checking TikTok's asynchronous processing status, so that state is not proof of publication. The owner chose to leave the TikTok send path unchanged for now rather than disable it, while keeping completion tracking, privacy and missing consent/source requirements as release blockers. This decision does not authorize production deployment or real uploads.
- YouTube and TikTok direct uploads now reject malformed or non-HTTPS session URLs, userinfo, custom ports, fragments and other hosts before sending video bytes; YouTube additionally requires the example upload path. PUT redirects are rejected rather than followed, and URL-bearing exceptions are replaced with a review message. `tests/publish_upload_url_guard_test.js` uses fake provider responses and blocks all real network. The allowed hosts/path come from [YouTube's resumable upload example](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol) and [TikTok's direct-post example](https://developers.tiktok.com/docs/en/content-posting-api-get-started), not a guarantee that these are the only URLs or that redirects never occur. This conservative guard may block legitimate uploads; verify provider behavior and operating requirements before rollout. TikTok privacy and completion/status limitations remain unchanged.
- Video storage paths are now treated as object keys rather than concatenated as raw URLs. Manual task creation rejects empty segments, dot segments, backslashes, percent escapes, controls and invalid Unicode before inserting; existing queued rows with such paths fail for review before storage or provider dispatch. Other filename characters, including spaces, Arabic, `?` and `#`, are encoded per segment. `tests/publish_video_path_guard_test.js` covers synthetic manual requests and all five dispatch paths without real network. This syntax guard does **not** prove object ownership, check existence or prevent use of another user's public object: the current manual endpoint still accepts keys outside the session user's prefix. Legacy keys containing literal percent or other rejected forms may be blocked and need review; inspect real key conventions and authorization policy before rollout without blindly replaying jobs.
- For the direct-byte uploads to YouTube, X and TikTok, the publisher reads a nonempty HTTP 200 storage response before starting the provider upload. An error response, 206 partial response, failed read or empty body stops that attempt; the YouTube upload length is based on the bytes actually read. `tests/publish_storage_guard_test.js` exercises these cases with synthetic storage and providers; credentials may still be refreshed before the read. This is not media validation: a 200 response may contain an error page, corrupt or truncated bytes, or an unsupported video. Meta platforms receive a URL and fetch it themselves, so this check does not apply to them. TikTok privacy and status limitations remain unchanged. Provider compatibility and memory use should be assessed before rollout.
- X media responses carrying `processing_info` now require `succeeded` before creating a post. For `pending` or `in_progress`, the publisher performs at most four mocked/tested status reads, verifies the same media ID and an error-free response, honors requested delays of up to five seconds and bounds each read to five seconds; longer delays, unknown/failed statuses, timeouts or inconsistent replies stop for manual review without another media upload or post. Absence of `processing_info` retains the previous behavior and does **not** prove video readiness. `tests/x_media_processing_guard_test.js` uses synthetic responses only. Crucially, the current video code still uses a simple POST and `amplify_video`; X's [media guidance](https://docs.x.com/x-api/media/introduction) recommends chunked upload for video, and its [upload reference](https://docs.x.com/x-api/media/upload-media) lists categories for the simple endpoint. This guard does not implement the chunked protocol or prove that the current upload works; review endpoint/category compatibility, time budgets and real provider behavior before rollout.
- For YouTube, Facebook, Instagram and X, a 2xx JSON response carrying an ID or readiness status alongside `error` or nonempty `errors` is treated as ambiguous, even when part of the operation may have succeeded. Empty `errors` and null error fields are allowed; the test fixtures cover both outcomes and avoid persisting the simulated error details. This conservative policy can stop on partial-success responses and needs provider-specific verification before rollout. TikTok's response convention is different and is not changed by this guard.
- Instagram container polling must receive a successful HTTP response with an error-free object and the exact `FINISHED` status before the publish request; `IN_PROGRESS` is polled as before, while errors, unexpected statuses, malformed replies and timeouts fail for review. `tests/instagram_processing_guard_test.js` exercises these cases with a synthetic provider and verifies a failed row is not dispatched again by this publisher. This is not evidence of provider-side processing or publication; an unrecognized legitimate status could stop a job, and provider status behavior must be verified separately before rollout.
- The live progress panel skips replacing identical polling results and preserves keyboard focus across changed results. When a focused video link disappears, focus falls back to the progress disclosure; if the panel becomes unavailable, focus moves to the named panel. This does not establish whether a run or provider upload succeeded. `tests/account_layout_browser_test.js` exercises these cases with synthetic data and network failures.

Chromium account editor and uncertain-save tests passed locally at 390px and 1280px; Quran preview retry passed as well. `tests/account_oauth_browser_test.js` drives Chromium through the real local start handler with fake session credentials, verifies the HttpOnly state cookie and aborts provider navigation; it does not test a real provider callback. The browser tests use stubbed services. Tests do not perform actual OAuth, modify production or send messages. The candidate queue/default SQL was exercised through isolated PostgREST, not production.
