# Candidate bounded video read (not wired)

The active direct-byte publisher still calls `response.arrayBuffer()` with no explicit response-size limit or read deadline. Video size, buffering copies, concurrency and provider upload times can exhaust a worker's resources or time budget; the 60-second gateway and 300-second cron budgets are overall invocation limits, not storage-read guarantees. The renderer requests a bitrate of 5 or 9 Mbps depending on canvas size (`public/js/reel.js`); this is not a measured size distribution or a safe maximum. A seemingly reasonable fixed cap could reject legitimate Quran videos. No production files or metadata were inspected to choose a limit.

`lib/publish_bounded_read_candidate.js` is an **unwired experiment**, not imported by the publisher. The caller must supply `maxBytes` and a total `timeoutMs`, and separately ensure the correct storage URL and ownership. It requires HTTP 200, no redirect, a nonempty byte stream, stops when decoded bytes exceed the cap, aborts on the deadline, and checks identity Content-Length when supplied. It does not compare a compressed Content-Length to automatically decompressed bytes. Errors are generic rather than exposing URLs. `tests/publish_bounded_read_candidate_test.js` uses actual Node fetch against a disposable loopback server and synthetic data: exact boundary, chunked size with no length, compressed response, error status, redirect, stalled headers, stalled or trickling bodies, and malformed/inconsistent mocked lengths. It does not connect to Supabase or any provider.

**Limits:** A buffer and chunk list may coexist and X's Blob/FormData and other upload paths may introduce additional copies; a bounded byte count is not a hard peak-memory bound. A huge chunk can be allocated by the transport before the application checks it. An abort deadline depends on fetch/stream honoring its signal and on the event loop running; it cannot interrupt arbitrary code or undo token refresh/provider calls that happened earlier. A timeout or size refusal marks nothing by itself: existing queue result handling, ambiguous outcomes and no-retry behavior must be preserved when integrated. No response check proves a valid, complete or audible video; size limits must never silently trim recitation. Meta's provider-side URL fetches are outside this candidate.

## Concurrency experiments

`publishTargets` currently starts all targets with `Promise.allSettled`; a failure does not cancel sibling jobs. `tests/publish_bounded_read_concurrency_candidate_test.js` calls that real orchestration with a **fake publisher** using the candidate reader: three loopback streams run concurrently, an oversized one fails, a valid one succeeds and a stalled one times out. This tests neither actual queue updates nor real provider behavior and does not add a concurrency limit to the application.

`node scripts/measure_bounded_read_candidate.js` samples memory in separate local Node processes using generated 4 MiB byte streams, no video, network or provider. One run on Node v22.22.3 recorded: 1 read → 4 MiB returned, 43.94 MiB baseline RSS, 58.18 MiB sampled peak RSS and 8.01 MiB sampled peak ArrayBuffers; 4 concurrent reads → 16 MiB returned, 43.57 MiB baseline RSS, 89.03 MiB sampled peak RSS and 32.20 MiB sampled peak ArrayBuffers. These are individual synthetic observations, not guarantees, exact allocation accounting, a production benchmark or a basis for selecting a limit. Sampling may miss peaks, RSS includes the runtime, and real HTTP, rendering and provider buffering may add substantial memory; GC and platform behavior vary. Never extrapolate linearly as a safe capacity calculation.

Before integration, determine a reviewed cap and deadline from supported media, user expectations, deployment memory and invocation budgets, concurrency, actual storage compression/redirect behavior, and provider upload constraints. Test failure, cleanup, stream errors, resource use and all three publishers with mocks and an isolated system; evaluate legitimate legacy files and make limit errors actionable. A separate per-batch limiter experiment is described in `docs/publish-batch-limit-candidate.md`; it is not wired to the application and does not limit other processes. A global/per-user concurrency strategy also needs design, including multi-process workers and partially completed sends; a per-read limit alone does not control aggregate memory. This experiment alone makes no operational or production change.
