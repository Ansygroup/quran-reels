# Existing queue rows and video-key scope

New manual task creation checks that the first key segment exactly matches the session user ID. The publisher also checks the **claimed row returned by the database** before connection selection, token refresh, storage access or provider dispatch. This applies to historical rows, direct inserts that reach this publisher, the `queue_id` path and cron. A mismatch or malformed path is marked failed for review using the existing conditional finalization; an unconfirmed finalization remains unconfirmed. Failed rows are not automatically retried. The owner explicitly chose to block mismatches for review, accepting potential interruption of legitimate legacy/shared keys.

`tests/legacy_queue_video_scope_evidence_test.js` uses actual manual and cron entry points and publisher with a synthetic DB, credentials and fetch replacement that blocks **all** network. For cross-prefix and malformed keys, both entry paths on all five platforms fail before even reading connections or attempting network; the test also changes the claimed path relative to the initial snapshot and simulates a lost finalization response. Same-prefix keys still reach a mocked network request. `tests/postgrest_publish_claim_integration_test.js` checks a cross-prefix job and a lost failure reply against disposable PostgREST, without real providers. This does not establish the existence or absence of such rows in production or prove real storage/provider behavior.

The check is a naming boundary, **not** proof of object ownership, existence, media validity, access control or immutable storage content. It cannot stop an old deployed publisher that ignores it, privileged writers or object replacement, an already-in-flight request, or guaranteed duplicates. All requests and fixtures here are synthetic. It may block legitimate historical or shared keys: review conventions and affected tasks before release, without blindly replaying them. The source-code schema describes public reads from `reels` and prefix-scoped client writes; it is not evidence of current production bucket configuration or policy. Any production read, write, rollout or provider test needs separate authorization and safe isolation.
