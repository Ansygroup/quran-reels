# Existing queue rows and video-key scope

New manual task creation now checks that the first key segment exactly matches the session user ID. It is not storage ownership verification. That check does not cover existing queue rows, the `queue_id` manual path, scheduled cron dispatch, direct database writes, or an already-in-flight provider request. The source-code schema describes public reads from the `reels` bucket and prefix-scoped client writes; this is not evidence of the bucket configuration, access policies or object keys currently deployed.

`tests/legacy_queue_video_scope_evidence_test.js` uses the actual manual and cron entry points and publisher with a synthetic DB, credentials and fetch replacement that blocks **all** network. For an existing `scheduled` row owned by `owner` with key `other/video.mp4`, both entry paths reach a simulated request for all five platforms: YouTube, X and TikTok attempt storage reads; Facebook and Instagram include the public video URL in a provider request. The simulated request fails and the mock row ends failed. This does not establish the existence of such live rows, that the storage object exists, or that any real transfer or provider action occurred.

A possible branch change would check the **claimed row returned by the database**, before connection selection, token refresh, storage access or provider dispatch, requiring its normalized key to have the row owner's exact first segment. A mismatch could then be marked failed for review using the existing guarded finalization; an unconfirmed finalization must remain unconfirmed. This is not yet implemented. Checking only the previously read snapshot is insufficient if the persisted key changes before claim. Such a restriction would also stop legitimate historical/shared keys outside that convention, and failing a scheduled job is an observable change to queue state. It cannot prove object ownership, stop a privileged writer or object replacement, cancel a request already sent, or protect a legacy deployed publisher that ignores it. It must not trigger automatic retry.

Before applying a guard to existing tasks, choose explicitly between (1) failing mismatched rows for review rather than contacting a provider, accepting potential interruption of legitimate legacy tasks, or (2) leaving current behavior while assessing the key conventions and a migration/review process. Production data and video uploads are outside this test. Any production read, write, rollout or provider test needs separate authorization and safe isolation.
