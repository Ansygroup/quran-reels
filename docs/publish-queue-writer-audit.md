# Publish queue writer audit (branch snapshot, local only)

This is a bounded source review, not an inventory of live deployments, database grants, policies, triggers, third-party clients or every historical release. No production data or metadata was queried for this review. Search included repository references to `publish_queue` in `api`, `lib`, browser JS, migrations, tools and candidate SQL; a dynamically constructed or external writer would not necessarily be found.

| Path | Current behavior and relevance |
| --- | --- |
| `api/_publish.js` | Existing row: reads by owner then calls `publishRow`; a failed row is blocked there. New immediate jobs are inserted as drafts and dispatched only after representation is verified; future jobs are scheduled, so a lost response can leave a live schedule. |
| `lib/autopilot.js` `queueTargets` / `publishTargets` | Inserts verified draft batch, then passes the returned rows to the publisher. A lost insert reply does not itself schedule the batch. |
| `lib/publish.js` `publishRow` | Claims only `scheduled` or `draft`, conditional on ID, owner, prior status, platform and connection ID; finalization checks only ID, owner and `publishing`. No claim revision or attempt generation. |
| `api/cron/publish.js` | Reclaims stale publishing rows then selects scheduled rows and calls the same publisher. |
| `lib/autopilot.js` `reclaimStalePublishing` | Conditionally changes expired `publishing` to `failed`; it does not stop a worker or provider request. `retryPublishFailed` reads failed rows and reports them blocked, not rescheduled. |
| `lib/autopilot.js` `ensureQueueRow` | No call site found outside its definition and `__test` export in this branch. It rejects a found failed row, conditionally changes a found draft or scheduled row to scheduled, or inserts a scheduled row if none was found. Not proof that old versions or external callers cannot reactivate. Reuse needs separate review: its deduplication and return-evidence handling are not equivalent to the newer draft-batch path. |
| `sql/schema.sql` | Defines an owner-scoped `FOR ALL` RLS policy. The checked-in schema alone does not establish current production grants, RLS configuration, API exposure or safety of direct client writes. |
| `sql/operations/candidate_account_table_acl.sql` | Separately proposed, **not deployed**: revokes direct table and column access for client roles in disposable tests. This is broad, can break clients and cannot prevent service-role or external privileged writers. Do not apply based on this audit. |

A comparison with locally available `origin/main` shows an older `ensureQueueRow` definition that could change a found `failed` row to `scheduled`; this is a code observation, not proof that the helper was invoked in a live version or is deployed now. The current branch's ordinary failed-row retry does not perform that transition. Other systems and privileged writers remain outside this review.

`tests/postgrest_channel_candidate_http_test.js` (foundation phase) uses **disposable** PostgREST with deliberately broad fixture grants and owner RLS plus the isolated account-target candidate triggers. It demonstrates that an authenticated owner can change their fixture row from failed to scheduled directly, while a different owner cannot. That demonstrates what those fixture permissions allow, not what production currently allows. The later guarded phase tests the separate candidate ACL revocation; neither phase changes a real database.

`tests/publish_reclaim_race_test.js` also demonstrates a separate stale-claim ABA: a worker holding an old `scheduled` snapshot can claim after an independent writer changes the same row through `publishing`, `failed`, and back to `scheduled`, and start a second synthetic provider request. This is conditional on that independent reactivation, not a claim that the branch's retry path does it. The candidate attempt generation in `candidate_publish_attempt_generation.sql` can fence a **cooperating finalizer**, but by itself does not compare a revision from the initial scheduled snapshot, prevent a stale claim, cancel in-flight requests, or stop legacy status-only finalizers. Preventing a stale claim needs a separately designed server-owned row/transition revision and coordinated readers and writers; even that cannot undo a request already sent or guarantee provider-side idempotency.

Before integration: audit actual deployed versions, all API/SQL roles and clients, policies and indirect triggers, lost responses and existing in-flight jobs; design and test claim versioning, finalizer fencing, failure handling, permissions and staged compatibility/rollback. Avoid resetting or replaying ambiguous jobs without reviewing the provider. Any real environment test or schema/ACL change requires separate approval and an isolated environment.
