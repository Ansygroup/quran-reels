# خطة نشر متدرّج لحماية إعدادات الحساب

**الحالة: تحضير ومراجعة فقط؛ لا يُنفّذ SQL ولا نشر إنتاجي من هذه الوثيقة تلقائيًا.** آخر فحص إنتاج قراءة فقط في جلسة التحضير؛ يجب إعادة التحقق قبل التنفيذ لأن المخطط والنسخة قد يتغيران. الاختبارات المعزولة لا تضمن سلامة الإنتاج.

## خط الأساس والعوائق

- نسخة Vercel الإنتاجية المرصودة `0aeba87b7bcad57c63c53a809bc955c3807ba0a1` (نشرة `dpl_zA9Sz2iazHC63mAtcBBCFbLAgZwq`، READY/PROMOTED). يجب التأكد من النسخة الفعلية وإمكانية التراجع قبل الإجراء؛ لا يعني بقاء النشرة قابلة للتراجع أن قاعدة البيانات ستتراجع معها.
- Supabase مشروع `lbblhpscncqsyzvuujpw`: فحص البيانات الوصفية أظهر غياب `autopilot.settings_revision` ودوال `save_autopilot_guarded` و`set_autopilot_enabled_guarded` و`link_autopilot_platform_guarded`. الهجرة الخاصة بالخلفيات `20261112225405` مسجلة؛ جدول الخلفيات ومشغّل تنظيف الخلفية موجودان. الإنتاج يحتوي أيضًا العمودين `daily_count` و`youtube_connection_ids`.
- إصدار الحساب المحلي يحتاج العمود والدوال؛ نشره أولًا قد يجعل لوحة حساب موجود تُرفض كبيانات ناقصة، ويعطل الحفظ وتغيير الحالة وعمليات الربط التابعة للدالة. لا تختبر عمليات الدخول أو الحفظ أو الربط أو التشغيل في معاينة Vercel الحالية: تهيئتها تستخدم قاعدة الإنتاج.
- تم توفيق لقطة مساحة العمل على الفرع الحالي دون دفع قسري: `3f534c5f` خلف `5c7bb1d8` ويحتفظ بمحتوى العمل، و`main` السابق `0aeba87b` سلف للفرع. قارنت لقطة العمل بفهرس مؤقت قبل التوفيق ووجدت نحو 102 ملف مختلف عن الفرع البعيد، بينها نماذج غير موصولة؛ لا يعني ذلك أن كل الملفات مناسبة للنشر. راجع الفرق النهائي ضد `main` وافحص أن الفرع لم يتغير قبل الإصدار، ولا تستخدم force push.
- ما زال كود الخدمة القديم والكتابة المباشرة المصرح بها قادرين على تجاوز المقارنة. اختبارات ACL المرشحة لا تثبت التوافق مع كل عميل أو كاتب خارجي؛ لا تشمل هذه الخطة تفعيل مسودات `sql/operations/candidate_*` أو منحها/سحبها. مراجعة `docs/account-settings-concurrency.md` و`docs/account-page-review.md` لازمة قبل أي تعهد بحماية شاملة.

## حدود الحزمة والتحقق قبل الإذن

1. جرد التغييرات منذ النسخة الإنتاجية ومنذ الفرع البعيد، وتحديد الإصدار المقصود، واستبعاد أي أداة اختبار أو نموذج غير موصول من الاستخدام الإنتاجي. راجع بخاصة OAuth وتجديد التوكن والفصل والطابور: تم اختبارها بمحاكاة لكن لم يُختبر جميع المزودين الحقيقيين، وقد يختلف سلوكهم. افحص عدم تعديل نص القرآن أو نشر بيانات اصطناعية.
2. شغّل الاختبارات على نسخة الإصدار النهائية، بما فيها `npm run pretest` وDOM ومتصفح حقيقي واختبارات PostgreSQL وPostgREST المعزولة والصلاحيات والتزامن. شغّل GitHub Actions على **نفس SHA** المقترح؛ نجاح الفحوص على SHA سابق لا يثبت نتائج أي تعديل لاحق. فحص HTTP القنوات المرشح نجح في حاويات معزولة، وليس على Supabase. لا تستخدم حسابات المستخدمين أو فيديوهات حقيقية لهذه الاختبارات.
3. طابق مخطط الإنتاج فعليًا مع متطلبات الهجرتين، بما يشمل الأعمدة والقيود والأدوار والـRLS والـtriggers والوظائف الحالية ومالك الدوال وصلاحيات تنفيذها. فحص الأسماء وحده غير كافٍ. أكّد أن خاصية النسخ الاحتياطي/الاستعادة متاحة وأن صاحب المشروع يعرف أثرها قبل تغيير المخطط؛ لم نتحقق هنا من توفر نسخة احتياطية أو استعادة مجربة. راجع أقفال `ALTER TABLE` وزمنها وتعارض الجدولة وخطة التوقف قبل اختيار نافذة الصيانة.
4. تأكد من هوية كتّاب الإعدادات، بما فيها الخوادم القديمة والعملاء المباشرين و`save_custom_reel`، وإمكانية التعامل مع النسخ المخبأة والطلبات الجارية. خلال فترة التوافق الدوال الإضافية لا تمنع الكتاب القدامى من تجاوز CAS. لا تفعّل مسودات سحب الصلاحيات قبل إثبات توافق كل المسارات والموافقة على آثارها.
5. تأكد من عزل الاختبار الفعلي. فرع Supabase السابق رُفض لخطة الاشتراك؛ GitHub Actions/PostgREST المحلي ليسا Supabase إنتاجيًا. لا تغيّر خطة الاشتراك أو تنشئ مشروعًا جديدًا لتجاوز القيد دون إذن منفصل. راجع تعيين بيئات Vercel وcron و`SITE_ORIGIN` وعنوان قاعدة البيانات قبل أي معاينة أو اختبار، ولا تشغّل اختبارًا يمكن أن ينتج فيديو أو يرسل إلى مزود حقيقي.

## تنفيذ مقترح بعد إغلاق العوائق وموافقة صريحة على SQL

- قبل النافذة: اعرض للمستخدم SHA الإصدار، فرق الملفات، نص الهجرتين ونتائج الاختبارات، وإجراءات التوقف والتراجع مع المسؤول عنها. لا تُطبّق خطة لم تعد مطابقة للفحص الحالي. احصل على موافقة محددة على تغيير قاعدة الإنتاج، منفصلة عن طلب النشر العام.
- الهجرتان المقترحتان فقط، بالترتيب: `sql/migrations/20261113_guarded_autopilot_settings.sql` ثم `sql/migrations/20261114_guarded_autopilot_actions.sql`. الأولى تضيف مراجعة ودالة حفظ وtrigger؛ الثانية تُعدّل دالة trigger وتضيف دالتي التفعيل/الإيقاف وربط المنصة. راجع النص الفعلي والـSHA قبل التنفيذ وتوقف عند أي إخفاق أو نتيجة غير متوقعة. لا تُدرج مسودات الصلاحيات الأخرى ضمنهما.
- بعد SQL وقبل كود الحساب الجديد: تحقق قراءةً فقط من العمود، تعريف الدوال والـtrigger، ملكيتها ومنحها وتاريخ الهجرة، وظهور مخطط PostgREST دون إجراء كتابة على حساب حقيقي. تحديث schema cache لا يثبت صحة كل طلب؛ لا تعتبر الإعدادات محمية من الكتاب القدامى.
- بعد تحقق الهجرات: حضّر إصدارًا من الفرع الحالي دون force push، وتحقق من CI على SHA نفسه. استخدم مسار النشر المعتمد للمشروع، وتحقق من READY ومن ربط الإنتاج بالـSHA المقصود. لا تدمج أو تنشر نسخة أقدم تتجاوز إصلاحات `main`. أي اختبار تسجيل دخول أو حفظ أو ربط في معاينة تتصل بالإنتاج يحتاج خطة وبيئة اختبار معزولة أولًا.
- بعد النشر: راقب الحالة والأخطاء قراءةً فقط وتحقق من نسخة الأصول وعامل الخدمة ومن أن الـcron كما هو. لا تختبر بإنشاء مهمة أو فيديو أو بتفعيل أتمتة حساب. تابع تعارضات الإعدادات وفشل الحفظ والربط ومخاطر التوكنات؛ يجب وضع مسؤول مراقبة ومدة زمنية مناسبة قبل البدء.

## التوقف والتراجع

- إذا فشلت الهجرة أو تعذر إثبات حالتها، **توقف**: قد تكون إحدى الهجرتين طُبقت دون الأخرى. لا تُعِد طلب SQL عند فقد الرد قبل فحص سجل الهجرة وتعريف المخطط. لا تنشر الخادم المعتمد على دوال غير مثبتة أو schema cache غير متحقق.
- إذا فشل بناء/نشر الكود بعد إضافة المخطط، أبقِ إصدار التطبيق السابق مع مراقبة الكتاب القدامى؛ المخطط الإضافي لا يضمن حمايتهم من التعارض. لا تُسقط الأعمدة أو الدوال أو الصور لمجرد التراجع عن التطبيق، ولا تستعد قاعدة كاملة فوق بيانات حديثة دون خطة منفصلة وموافقة.
- التراجع إلى نشر Vercel السابق يعيد سلوك الخادم القديم غير المحروس، وقد يعيد مخاطر التعارض. تدقيق مخطط وامتيازات لحظة التراجع لازم؛ إعادة توجيه النطاق لا تُلغي طلبات جارية أو تحديثات أو عمليات رفع حدثت. لا تفترض أن فشل استجابة المزود يعني عدم النشر، ولا تعِد المحاولات تلقائيًا.
